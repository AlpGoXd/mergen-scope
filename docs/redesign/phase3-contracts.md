# Phase 3 contracts for review

Status: proposed, not implemented. Base `517fb4c5a0d2cf9865bf977a49f85d552bc8ef9b`; source is v3 spec sections 3–5 and Phase 3, plus plan 3A–3F. Written spec supersedes drawings. Reference boards 43 and 45 were inspected; the latter's card presentation is superseded by AC-3 board 03. No IQ/Polar expansion.

## Existing hazards and identity

`Trace.id` and display trace/dataset IDs already represent underlying identity; `Trace.name` is an internal persistent unique key used across stores, not the user-facing `dn` display label. Do not create a second independently mutable identity. Proposed transition retains that unique internal key for the existing membership and marker adapters, with `id` as underlying identity and a validated one-to-one lookup; all rename operations change only display labels, not internal keys. Same-name file copies obtain distinct file/trace IDs and internal keys. If an input has collisions or duplicate IDs, reject or deterministically normalize at the migration/import boundary; never silently conflate. Tests must prove rename, replacement and same-name copy preserve the correct membership and marker associations. A replacement maps surviving parameters by stable file/parameter identity, not a display-name guess.

`Pane.id` is opaque and stable, never derived from array position or count. Array order determines visual numbering; creation allocates a fresh ID not reused during the session, including after undo/redo. Preserve valid legacy IDs on migration. Cleanup receives actual ID sets, not `pane-1..N`.

## Placement and pane contract

`tracePaneMap: Record<InternalTraceKey, readonly PaneId[]>` is the sole authoritative membership mapping. Explicit `[]` means intentionally unplaced and never triggers automatic placement. Missing membership is materialized as `[]`, never as a default pane; only an explicit opening/placement action chooses a destination. Default imports must invoke the opening planner so they are not silently left unplaced. Normalize removes nonexistent/duplicate pane references but does not invent one. Compatibility is checked against all current pane members by canonical X-unit group (not filename, label or visual index). An empty pane adopts its first known X group; unknown units cannot bridge different known groups or silently join a known incompatible group.

Separate commands: `addMembership(trace,pane)` copies without moving existing copies; `removeMembership(trace,pane)` removes only that copy, retaining markers; `moveMembership(trace,from,to)` validates and moves one copy atomically; `deleteTrace` removes all memberships and its trace-owned markers. Results are discriminated success/failure with a user-facing reason; a failed operation changes nothing. Pane type compatibility is checked for Chart/Smith/Table; incompatible type switches return a plan and do not discard state. Smith accepts eligible network reflection data with proven matching underlying complex samples, including the same scalar Sii display trace placed in both Chart and Smith; Sii supports all diagonal ports while converted Z11/Y11 require valid file Z0; Table does not manufacture unsupported plot data.

`planPaneRemoval(panes, traces, removedPaneIds: readonly PaneId[])` (typed pane/trace records may carry required context; a wrapper is permitted) is pure, supports multiple removals including layout and type-switch operations, and returns affected memberships, per-trace moves/unplaced results, line/zoom cleanup and confirmation requirement. Existing copies outside removed pane remain; for a trace with no other copy, search compatible remaining panes in visual order with previous panes before subsequent panes as specified, otherwise preserve explicit `[]`; never use a different-unit fallback. A plan removing every pane is refused; simultaneous removals are planned against the complete remaining set, not applied sequentially. Applying a reviewed plan is one transaction and preserves remaining pane IDs/settings/order. Pane create copies target settings; duplicate pane has explicitly copied memberships/settings, not shared mutable objects. Stable target is an ID, not an index.

One canonical browser preference determines maximum pane creation: default 4, experimental 8; storage unavailability falls back safely to 4 and never breaks the app. Load preserves valid saved 5–8 even when preference off; no silent truncation, and new additions are refused until under the current limit or preference is enabled. Workspace does not store this app preference. Per-pane settings carry type, X link group, grid/zero line and individual visibility including sample dots/readout names; v5 also defines stable defaults for Smith Z/Y/Z+Y grid, labels, direction cues and readout, plus layout preset/order/sizes, so Phase 5 presentation does not silently change the wire shape; minor grid is removed from user-facing contract. Presets and types preserve identity; type-switch validation exposes reasons. Phase 5 owns final rendering/layout presentation.

## Marker, line and interaction contract

Markers belong to trace identity (internal key resolved to ID) and render in each pane containing that trace; visibility affects presentation, not identity. Persist absolute requested/resolved position. Each v5 marker has a required stable marker ID; deltas refer to that ID. Indices exist only in the legacy adapter, where valid references are mapped to IDs; changing reference changes only relationship and derived delta values, never absolute coordinates. Deleting the reference, whether singly or in a bulk deletion, converts dependent deltas to normal markers at the same absolute positions and later marker creation must never auto-attach them; removing multiple markers remaps references deterministically. Selection is stable across array reorder/removal. No persistent Normal/Delta mode: explicit transient `armed` command describes normal placement or delta-from-reference, cleared by Esc/completion. Transient arm/hover is excluded from workspace and undo.

Vertical lines link only among panes in the same X-unit group; horizontal lines cannot link and expose a reason. Treat a linked line as one logical line with group membership/ID, or a validated synchronized representation, but never link unrelated units or create orphan mirror lines on pane reordering. Linked V membership is recomputed whenever a pane X group changes, not just when it is removed. Remove pane and unlink affect only valid members; ref-line cleanup uses actual IDs. Existing v4 grouped/mirrored lines migrate without changing values. Marker/reference drag captures pre-drag state, creates one history entry per completed gesture, not one per mouse move; Esc/cancel restores pre-drag state without an entry.

## Transaction/history boundary

Portable JSON is not a lossless undo format. Use an in-memory, bounded history of actual immutable state/mementos covering file records **and rawFileData**, wizard queue/config, trace/derived lineage and visibility, pane membership/order/settings/zoom, markers, reference lines, analysis results/open state and persisted workspace UI state. Exclude browser preferences and transient hover/armed/drag presentation. Retain immutable large sample arrays by structural sharing; do not deep-copy or serialize them on every change. Bound: 50 logical entries and 128 MiB conservative retained-unique-data estimate. At each commit or undo/redo, account identity-distinct retained objects across past/future mementos, counting UTF-16 strings at 2 bytes/code unit, numeric array slots at 8 bytes, and object/array/entry overhead at 64 bytes plus 16 bytes per property/slot; traverse cycle-safe and count shared identities once. Prune oldest past entries until both limits hold, then oldest future entries if needed; if the new action itself cannot fit, clear history and notify that it cannot be undone. Recalculate from reachable history after each change; current live state is excluded from retained-history estimate; if a single change exceeds the cap, preserve current operation and do not offer a fake Undo, clear expired history consistently, and show explicit user feedback. Test both limits and the oversized-action path. Exact accounting/cap must be measurable and tested before shipping.

One logical command owns all cross-store writes: file open/replace/remove, trace delete, pane removal, marker/line changes and complete drag. Begin captures before-state; commit captures after-state only after all relevant state updates are applied; no-op creates no entry; any new committed command clears redo. Undo/redo restores all slices together. To avoid React-provider effect races, the preferred implementation is one aggregate transaction reducer/provider exposing typed slice context adapters, with no duplicate independently mutable legacy stores, with reconciliation and orphan cleanup performed deterministically inside the same transition; no observer of every render and no async effect-driven partial restore. If adapting current providers instead, prove an explicit restore epoch/barrier prevents every reconciliation/cleanup effect from running against mixed generations and tests check after effects settle. Never call portable `getSnapshot` as history: it hardcodes result fields and loses raw text. Nested commands coalesce within the owning action; async file reading/parsing completes before atomic command commit, then its plan is revalidated against the latest state revision (pane existence, X group, limit preference, duplicate and workspace decision); do not restore or commit a stale snapshot over intervening user edits. Cancel, invalid workspace and failed replacement leave the prior data unchanged. Failed new data imports persist unreadable error rows and count in the same logical batch/Undo; mixed workspace and data applies the successful workspace first and then data successes/errors in one ordered command. An undo during pending parsing changes the revision and forces replan before commit. No-op retains redo; failure/no-op does not consume visible IDs (or a documented monotonic allocator may advance invisibly while never reusing IDs). Undo toast is a callback into the same history, not a second history.

## Opening and registries

A pure opening planner consumes classified input descriptors, current files, target/explicit-drop pane, unit groups, pane limit and chosen duplicate/workspace resolution; returns typed ordered steps or refusal reason without mutating stores. Explicit incompatible pane drop is refused; elsewhere target → first compatible → new under limit → unplaced. Defaults: one trace for single-trace data, S11 dB for one-port, S21 + S11 dB for two-port, 3+ port no plotted traces and matrix open; wizard-selected Y or recognized numeric columns up to eight. Same-name cancel is no-op; copy creates distinct stable identity; replace commits only after successful parse and preserves matching parameters' colors, memberships and markers. Workspace is applied first, then data; replacing a nonempty workspace asks, failed workspace parse does not clobber existing data. UI integration of entire opening frame and Edit columns remains Phase 7/4, but pure planner and real action paths required by this phase must be tested rather than simulated.

Define typed registries for data-kind, pane-type and analysis capabilities using existing dataset/display trace model. Analysis contract: `kind: math|measure|view`, metadata id/title/description, `appliesTo(trace)` returns allowed or explicit reason, parameter schema, pure compute contract and declared outputs (number/table/overlay/trace). Existing analysis registry/algorithms remain in use; do not assert card migrations complete until Phase 7. Network-only and density-unit restrictions must be explicit and tested.

## Workspace v5 and preference boundary

Capture valid raw legacy pane IDs/order/memberships before any full old normalizer; bypass its destructive four-pane layout clamp and incompatible fallback while reusing legacy file/data normalization. New v5 wire type explicitly represents pane membership arrays, pane identities/order/type/settings/layout and target, selected trace, markers and reference line identity/relations, matrix open per file, and actual saved wizard configuration. Store workspace data, not `system/light/dark`, pane-limit or other browser preferences. Loading v4 and older uses existing v4 normalization, then a separate v4→v5 adapter. Convert each valid scalar assignment into a singleton; preserve explicit empty membership in v5; filter invalid pane references without cross-unit fallback. Copy legacy global showDots to each pane. Derive stable marker references from valid v4 indices; invalid references convert safely without moving marker. Preserve legacy `glass` as an ignored workspace appearance field, never overriding browser theme. Save only v5; reject malformed/future version in either package envelope or snapshot body, including version mismatches, before mutating current state. Migrate files/datasets/display traces, analysis data, wizard configuration and matrix state without fabricating unavailable raw inputs. Loading 5–8 valid panes does not change preference or truncate. Restore is atomic with same effect/reconciliation barrier as history.

## Delivery sequence and acceptance

1. Freeze and review these contracts (3A), inventory all consumers and v4 fixtures; resolve any ambiguity with root before coding.
2. Identity/membership/pane model and pure planners (3B); update dependent consumers as one coherent slice; after every ChartPane edit run e2e immediately.
3. Marker/line and armed state (3C), pure opening/registry contracts (3D), then transaction coordinator/history (3E); migrate files and shared state together in v5 (3F), avoiding a partially migrated runnable tree.
4. Mounted provider integration tests must verify composite state after React effects settle, immediate consecutive commands, and undo during pending async parse/revalidation, not just pure reducer tests. Behavioral tests include nonsequential IDs, explicit `[]`, multiple copies, unit-safe removal previous-before-next, type incompatibility, 4/8 and preference-off reload, marker delta reference/change/deletion, V/H links, wizard/raw-source and analysis preservation across undo/redo after effects settle, async failures/cancel and same-name copy/replace, mixed workspace/data sequence, bounded history, gesture coalescing and redo invalidation. Golden older workspace fixtures must prove preserved nonsequential IDs, raw 5?8 panes, invalid membership filtering and legacy dots before normalization; malformed/future rejection, round trip and no preference leakage are mandatory.
5. Full five gates plus visual comparison for touched UI, independent review, exact manifest of tracked/untracked/binaries, and root integration/verification. No completion claim while required behavior remains deferred; Phase 4/5/7 presentation work remains separately tracked.
